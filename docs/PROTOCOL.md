# 夜魔 X OLED 通信与像素格式

本记录描述 ROG Azoth X 经 ROG OMNI 接收器及 USB 有线上传自定义画面的已用参数。其他键盘、固件和蓝牙方式需要单独验证。

## 证据来源

通信命令来自原厂 `GearLink_KBApi`、`GearLink_KBAgent` 和 `GearLink_KBService` 组件的本地分析。绘图区尺寸来自本机 ASUS OLED 代理日志。字体修复还经过软件检查、真实上传和用户目视确认。

原厂二进制、完整反编译源码、设备唯一标识及原始日志保留在本机，不随此仓库分发。仓库包含自行编写的工具、协议说明及经过筛选的修复证据。

## 已使用的参数

| 项目 | 值 |
|---|---|
| 接收器 VID / PID | `0B05:1ACE` |
| 本机配对键盘 PID | `0x1C25`（7205） |
| 控制通道 | HID usage page `0xFF00`，report id `2` |
| 接收器报告长度 | 64 字节，包含 report id |
| 绘图区 | 208×64 |
| 灰度 | 每像素 4bit，16 级 |
| 每帧数据 | 6656 字节 |
| 每包画面数据 | 59 字节 |

上表是接收器路径。有线接口在本机确认如下：

| 项目 | USB 有线值 |
|---|---|
| 键盘 VID / PID | `0B05:1C24`（7204） |
| 控制通道 | usage page `0xFF00`，report id `0` |
| 输出缓冲区 | 65 字节，首字节为 0 |
| 输入报告 | 64 字节，从命令字节开始，不含报告 ID |
| 每包画面数据 | 60 字节 |

接收代码为无编号 USB 输入补上首字节 0，再交给统一的确认包解析器。USB 线和接收器同时插入时，配对表不表示无线链路当前可用；`show.connect` 会要求候选接口响应位图模式命令后才选用。

## 像素顺序

图像按行从上到下排列，同一行从左到右读取。每两个像素合成一个字节：

```python
left = left_pixel // 16
right = right_pixel // 16
packed = (right << 4) | left
```

低 4 位是左像素，高 4 位是右像素。原厂 `MergePixel` 的关键逻辑是将第二个像素的 4 位字符串放在第一个像素前面，再按二进制转换为数值。

左白右黑应为 `0x0F`。如果写成 `0xF0`，相邻像素交换位置，产生文字梳齿。旧实现曾犯这个错误，现已修复。详见[教程](../OLED字体清晰化修复教程.md)。

## 实时时钟：单帧位图与重绘

默认 `show.py clock` 采用原厂音乐信息位图通道，保留自定义时钟布局。它不上传 GIF，也不采集音频。

命令为 `0x67`。接收器路径的 report id 为 2，有线路径为 0；下表字节位置包含这个首字节：

| 步骤 | 报文字节（包含 report id） |
|---|---|
| 设置位图 | `[1]=0x67, [2]=0`；`[5]=0`（仅信息位图），`[6]=0`（无频谱样式），`[7:9]=u16 包数`，`[9:11]=u16 宽度`，`[11:13]=u16 高度` |
| 上传画面 | `[1]=0x67, [2]=1`；`[3:5]=u16 递减包序号`，从 `[5]` 开始放数据；接收器每包最多 59 字节，有线每包最多 60 字节 |
| 触发重绘 | `[1]=0x67, [2]=2`，其余载荷全零 |

该载荷只有一帧原始 4bpp 数据，没有动画帧数和 duration 头部。208×64 下为 6656 字节。接收器需要 113 个数据包，加模式和重绘命令共 115 份报告；有线需要 111 个数据包，共 113 份报告。新建连接时，还会发送一次模式请求确认连接能响应。

模式和数据包逐包等待 ACK。重绘命令对应原厂 `SetSpectrumData`，原厂只写、不等待 ACK。实测仅上传位图会停在旧画面；加入全零重绘触发后，用户确认自定义时钟正常更新秒数，且没有滚动、闪黑。保留这一触发步骤，不要因为它名为频谱数据而删掉。

## 旧入口：自定义动画命令

命令为 `0x61`：

1. `sub=1`：设置本次总数据包数。
2. `sub=2`：逐包上传数据，等待相应 ACK。
3. `sub=3`：请求显示。

| 字节位置 | 内容 |
|---|---|
| 0 | report id |
| 1 | `0x61` |
| 2 | sub |
| 3～4 | 数据包剩余序号，小端；mode/show 中为 0 |
| 5～8 | mode 命令中的总包数，小端 u32 |
| 5～63 | data 命令中的最多 59 字节数据 |

数据块按源数据顺序递增发送，包序号从 `total - 1` 递减到 `0`。两者不是同一个计数方向。

动画载荷结构：

```text
u16 帧数
每帧对应的 u16 duration
所有帧的位图数据
```

旧动画入口发两帧相同画面，duration 均为 1000：总计 13318 字节，226 个数据包，另加 mode/show 命令。重复上传会打断显示，因此默认时钟不再使用此路径。ACK 表示收到命令，不能单独证明实物显示正确。

## 实测范围与待验证项

- 本机曾出现单帧上传后画面不更新，因此静态页沿用双帧方式。
- 本机双帧上传成功。更多帧的可靠传输和实际动画节奏尚未完整验证。
- 多帧 duration 的实际播放行为仍需实物测试。
- 待机息屏时，上传不能可靠代替按键唤醒。
- `0x62` 横幅命令已在设备唤醒后复测成功，但实物会滚动，不适合固定时钟布局。此前“不支持”的结论不能继续使用。
- 旧 CLI 的 `--wait-link` 参数没有在动画上传流程中完整接入；不要依赖它自动唤醒键盘。

日常使用优先选择 `show.py`。历史探测脚本的范围和限制见 [tools/README.md](../tools/README.md)。
